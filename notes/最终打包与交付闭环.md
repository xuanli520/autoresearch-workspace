# AutoResearch 最终打包、交付与返修闭环

更新：2026-09-27。配合[全流程指引](../AutoResearch出题全流程指引.md)、[运行手册](../部署与长程接管.md)、[目录治理](长程Agent脚本与目录治理.md)及[两题复盘](双题四并发长程Agent复盘-20260927.md)使用。

**最终交付是把已验证版本、可执行题包和真实证据交给接收方，并让对方能在干净目录准确恢复、构建、评分和审查。** 生成ZIP只是其中一个步骤。应从研究首轮就准备证据，结束后按冻结白名单生成提交副本，再针对实际压缩包验收。

共享 GPU 复验与交付口径：允许在不影响他人的前提下继续自己的 GPU 任务，不以其他进程出现本身触发停止。共享资源契约、峰值/余量/负载观测和真正的停止原因写入本题证据；不能把共享当独占或把无干扰观察写成硬隔离。旧中断/退出原件不因策略更新而改写，安全风险、用户停止与硬截止仍执行。

本文规定后续工作方式；本次没有重新打包、删除旧包、上传、执行训练或补做Harbor/GPU Trial。引用的历史PASS只代表其记录范围，不把静态检查提升为平台验收。

## 2. 先确定本次交付的是哪一种对象

| 交付对象 | 内容边界 | 接收方应知道的事 |
|---|---|---|
| 平台标准最终专家包 | 按本次正式Schema的workspace、expert_evidence、optimization_evidence及明确要求文件 | 三目录、必需文件和允许的包根内容须精确匹配；不能添加自认为有用的debug/QA目录 |
| 独立公开harbor_task包 | 该任务根的公开题面、配置、环境、Starter、测试入口与允许公开资产 | 不等于完整专家包；可信资产通过授权平台入口注入，不放进公开镜像 |
| 指定模型轨迹/优化证据分类包 | 用户明确要求的对应证据集合 | 依赖、来源版本、可单独审查范围和所需其他包写清 |
| 完整运行档案 | 原始事件、失败、模型、健康、部署/修复和历史包 | 专家私有保存，通常不等于可直接上传的平台白名单包 |

**每次发布只选择一个明确的交付profile与文件白名单。** 用户若要求多个分类包，为每类分别列范围；不能把完整档案直接压缩后称“标准最终包”，也不能把harbor_task ZIP当作包含研究证据。

本次09-27索引中的full_delivery包含README、SHA256SUMS、进展清单和较广的运行材料；其是否符合特定平台的严格三目录白名单，必须按该次交付profile逐项判断，不能仅凭命名或旧QA PASS推断。通用文档、索引、额外报告默认放包外，平台明确要求才进入包内。

## 3. 从第一轮就建立交付证据链

| 阶段 | 最低原件 | 汇总材料 |
|---|---|---|
| 协议冻结 | 方法/数据/seed/预算/聚合/checkpoint规则、B/U事前依据、源码和资产hash | formal protocol、comparison_summary |
| 正式B/R | 全seed原始指标、命令、起止/退出、stdout/stderr、模型、artifact/hash、新进程重载结果 | 均值、n−1标准差、提升及3σ/5σ说明 |
| Agent研究 | 模型/CLI版本、候选快照、真实事件、完整评分、失败、逐轮计时和排除区间 | 两条八字段轨迹、run_summary、时间审计 |
| 唯一best | 来源run/model/round、源码hash、选优规则与全协议结果 | best_method源码/入口/必要配置 |
| 干净复验 | 冻结环境、命令、候选身份、全seed、重载、结果及退出 | selection与revalidation摘要 |
| Harbor接入 | 同Trial config/result/reward/非空日志、任务hash及provider配置 | H01–H06范围与版本绑定 |
| 资源/健康 | 容器身份、实际负载、OOM/重启/资源记录；适用硬限额的真实越限证据 | 已观察范围与未验限制 |
| 发布 | 白名单、相对路径、文件和ZIP hash、解压及结构验证 | 唯一交付索引与说明 |

每轮保存的结果必须绑定当时源码，不从当前solution反推历史方法。最终best不能替换为Reference。缺失元数据写null并解释；不能为了JSON齐全制造时长、分数、日志或“重载成功”。

训练模型应按每个正式seed保留；同一个checkpoint反复评测不算独立训练。空reload.log本身不等于失败，但必须能从其他非空可信记录追踪实际重载与结果。无法追踪就标缺证据。

轨迹失败轮也要非空摘要，描述实际方法/工具动作与失败原因；没有方法动作就写运行器或请求失败。修复摘要不得改失败状态、failure_reason或null分数。每组轮数、有效轮数与run_summary对账。

## 4. 冻结版本与变更影响

冻结前写一份发布声明：release-id、题目/协议版本、来源目录与hash、唯一best来源、交付profile、白名单依据、目标Harbor/provider、已完成验证和未完成项。它放包外或正式合同规定位置，不能再造一份与进展清单竞争的实时状态。

已有不可变原件不改动；从已质检源复制到新的发布候选目录，再按白名单裁剪。白名单包含文件、必要空目录、执行权限与可接受符号链接策略。删除前确认保留材料的相对引用仍成立；不能删了日志/model后仍让JSON指向不存在的路径。

| 变更 | 应补的验证 |
|---|---|
| 纯文档、摘要空缺或索引 | 文本来源、JSON、链接、Schema、hash、白名单；通常不重跑训练 |
| 分片、压缩、目录移动 | 全套解压、成员集合、字节/hash、权限、路径引用、原始资产恢复 |
| Docker/依赖/Harbor版本/驱动 | 干净构建、真实目标Trial、受影响数值/模型兼容性；不得沿用不匹配动态证据 |
| 评分器、guard、资源合同 | 正常/失败/越限路径及真实执行边界、reward合同，分析科研结果是否受影响 |
| 训练器、数据、seed、预算、指标 | 重审正式B/R、评分锚点、比较与best复验；不能仅跑单元测试 |
| best源码 | 验证仍为真实Agent候选并重新完整复验；专家改算法不能沿用原来源 |

修复范围内证据足够后停止重复验证。用户已要求停止新实验时，完成授权内静态/无损检查并明确动态限制，不为“全部绿色”暗中重跑。

## 5. 白名单生成与公开隔离

生成时采用“允许什么就复制什么”，再用严格清单检查；不能只排除少数`.log`/`tmp`后把整个工作区带进去。逐项排除凭据、provider配置、SSH信息、宿主路径、缓存、镜像tar、构建层、临时debug、历史副本、编辑器文件、`.git`历史、`__pycache__`、Zone.Identifier等非合同项。

公开harbor_task与私有证据分别扫描。专家包可以含私有Reference和研究材料，但整个专家包不能挂给solver。可信评分数据只按平台注入合同提供，Hidden目录应按合同为空；不同私有资源的用途不能都叫“Hidden”。扫描镜像层、context、mount、环境和历史，当前目录删除秘密不消除旧层泄露。

路径必须相对提交包根，不含作者主机绝对路径或包外`..`引用。受管可执行入口保留Unix执行位。symlink若非合同必需应避免；必须使用时验证解压后目标仍在允许根内。校验JSON有限数值/null、TOML解析、Python语法、shell入口、数据manifest与协议一致；语法检查不要在包内生成pycache。

## 6. 大资产、离线分包与恢复

本次约束“每包小于300MB”实际按**严格小于300,000,000字节**校验，不按300MiB，也不把等于上限当通过。新任务采用其真实上限；压缩后测大小，不用原目录大小估算。

有两种不同分包方式，必须声明所用方式：

1. **独立ZIP分组。** 每个ZIP可单独解压，全部按同一根目录合并；成员通常互不重复。若允许重复，要求字节一致并在清单说明，不能靠解压顺序覆盖不同版本。
2. **文件级分片。** 超大资产拆为若干可校验分片，包内提供受管恢复入口；逐片hash/大小和重组后原文件hash都核对。若采用标准多卷归档，应明确工具及恢复命令，不混称独立ZIP。

本次视觉是离线资产分片与多个独立ZIP配合使用；不能随机取part01做完整任务QA，也不能从另一日期包借part补齐。包序号是发布的一部分，所有part都应在唯一索引内。

接收方在新的空目录中依索引解压全部part；拒绝绝对成员路径、`..`穿越、重复冲突和越界symlink，核对预期解压总大小并预留磁盘空间，避免错误包撑满系统盘。不要在已有源码目录上覆盖解压，否则旧文件会掩盖缺项。

恢复后逐文件比较源manifest：集合相同、字节与SHA-256相同、执行权限及必要空目录存在。资产重组验证原始hash而非仅数组shape；不能以重新计算的近似数据通过。声明数据是否完全离线，以及软件构建是否仍需公开软件源。

## 7. 三层验收必须针对不同对象

| 层次 | 被检查对象 | 能证明什么 |
|---|---|---|
| 源目录审查 | 冻结候选目录 | 内容、协议、已有证据、合法结构 |
| 实际ZIP审查 | 真实压缩包及全套part的干净解压结果 | 包是否完整、可恢复、成员/权限/hash正确 |
| 目标运行审查 | 解压所得题包、目标provider和真实Harbor Trial | 该发布版本能构建、执行评分、满足运行合同 |

完成前不能只检查源目录，也不能仅“ZIP CRC通过”就宣布可运行。CRC、密码学hash、路径/Schema、构建、科学结果、动态边界各解决不同问题。

建议验收顺序：

1. 确认冻结声明、唯一best来源、G01–G03、全部正式seed与两轨迹时间。
2. 按白名单生成新副本；核对文件、目录、JSON、相对路径、权限和秘密隔离。
3. 生成最终ZIP；测严格大小上限、CRC、成员清单与ZIP hash。
4. 全套在空目录安全恢复；对照source manifest，恢复资产并核对原始hash。
5. 在授权范围内跑受变更影响的真实构建/Trial/硬件验证；保存同Trial材料和退出状态。
6. 对解压结果做最后适用QA；记录适用范围及未执行项，不能覆盖旧失败。
7. 生成包外发布索引、hash和交付说明；再确认它们指向的是刚检查的文件。

如果第5/6步产生需纳入正式白名单的新增证据，先把证据回收到新的候选版本，再重做受影响的打包、hash和解压检查；最终ZIP不在生成后偷偷增删成员。

## 8. H06、QA16、QA21的交付前专项对账

**H06：** 从一个真实Trial保留config、result、verifier/reward.txt或reward.json、非空trial.log或test-stdout；确认task/交付版本、provider配置、正常结束、exception、日志调用链与reward优先级，逐键逐值一致。绑定manifest指出该Trial使用的实际任务文件hash。旧Trial对新包仅能证明未变部分，不能在绑定JSON里声称未运行过的新源码已验。

**QA16：** 每组单独列墙钟起止、有效区间与排除区间、原因、来源hash、去重规则和求和值；与run_summary逐值核对。本工作区默认至少10小时有效研究，训练型不使用7小时例外；本次11小时是具体运行目标。计时原件与审计数量可与轨迹数量不同，必须解释请求失败/不完整轮的缺失与零信用。

**QA21：** 八字段完整，method_summary去空白非空，round连续，时间与时区清楚，失败score为null，retained_best有可信评分/源码依据。摘要修复以真实事件为依据，不重写方法历史或成功状态。

GPU显存强制、健康观察和上述三项分别验收。专家侧不要求连续12小时soak，不能为了一个不适用门槛继续烧预算；真实硬件限额缺证据则如实列未完成，不能用“无需soak”豁免。

## 9. 唯一发布索引和交付说明

索引字段建议包括release/profile/task、来源manifest、每包路径/角色/part编号/字节数/SHA-256/成员数、依赖part、预期恢复根、预期总大小、验证记录路径、已知限制。字段名按既有工具Schema，不随意硬改；本次已有[交付包_20260927_INDEX.json](../交付包_20260927_INDEX.json)可作为事实入口，但不能将历史白名单未经审查套到新发布。

交付说明回答六件事：

1. 哪一套文件属于本次发布，哪些只是历史保留；每个part都列全。
2. 怎样校验、解压全部part和恢复数据；准确的任务根在哪里。
3. 实际Harbor版本、build context、执行入口、GPU/CPU和外部软件源需求。
4. 哪些可信资产不在公开包、由谁通过何种既有合同注入；不附密钥。
5. 哪些检查真的做过、对应哪个版本，哪些因授权或硬件缺失没做。
6. 研究与资源是否结束、证据在哪里、下一步验收由谁负责。

索引及说明从manifest生成或核对，不能人工复制旧文件名、大小和hash。摘要可以短，但限制不能藏在旧报告里。平台上传/对外发送只在明确授权后进行；本地打包完成不自动提交。

## 10. 返修不破坏历史

以新release-id保存整改：退回项 → 原始事实 → 具体修改 → 影响范围 → 必要重验 → 新包hash。旧源、旧ZIP、旧QA和失败仍保留；用户明确要求覆盖某名称时先归档旧字节与hash，再将新包移到该名称，索引记录替代关系。

收到退回先逐项复核，不因一项失败重做全部研究，也不因整体PASS忽略真实缺项。只修文档/摘要时不改分数；只修构建时不宣称算法提升；训练协议变更则重审科学证据。

不要在不同交付版本间拷贝通用“通过”报告。跨版本复用必须写出未变文件/协议/环境的hash依据和仍未覆盖部分；H06同Trial材料保留原貌，补充绑定说明不能伪造运行日志。

## 11. 清理、冻结和工作区闭环

长跑结束先保全研究与交付证据，再清理本次临时文件、构建展开目录、已关闭中间产物和已确认不再需要的自身资源。当前写入中的日志、唯一失败原件、正式seed模型、重载、best来源、同Trial材料和旧包不可删除。

最终标准提交副本内只留白名单；完整档案在专家私有archive中保留。包外验证报告、索引与清理记录让后续接手者知道“删掉的是可再生副本，留存证据在哪里”。按hash去重，避免在每个分类包旁再复制整份数据；接收方需要的重复内容则按交付合同保留，不为了磁盘节省破坏可用性。

更新题目进展清单：发布ID/索引、实际检查结论、未完成项、资源终态、剩余授权和下一步标准。通用手册只记录可复用经验；主机、PID、方法分数和实时状态留在题目私有材料。

最终完成判据：

- [ ] 来源、profile和白名单唯一；原始质检目录、旧包和失败证据保留。
- [ ] G01–G03、全seed模型/重载、两轨迹时长/摘要、唯一best及复验可追溯。
- [ ] 题面、代码、guard、资源和路径一致；动态未验项明确。
