# 长程 Agent 脚本复用、配置与目录治理

更新：2026-09-27。本文服务于准确、稳定、可接管、低维护成本的研究运行，配合[运行手册](../部署与长程接管.md)、[双题复盘](双题四并发长程Agent复盘-20260927.md)和[交付闭环](最终打包与交付闭环.md)使用。

**原则：通用逻辑只维护一份，题目差异由薄适配器与配置表达；每次运行保存其真实版本，临时排障集中放置，完成后只保留有解释价值的证据。** 不为整理目录重写可用脚本，不把“临时”作为绕过版本、参数、测试和清理规则的理由。

共享 GPU 策略同步：不因其他计算进程出现自动停止自己的训练；在不影响他人的前提下按实测峰值、显存余量、负载及调度约定继续共享，限制自身并发/资源并记录。资源耗尽风险、明确干扰、用户停止和预算到期另按合同处理。改变策略须新配置/发布，不能热改运行中源码；旧中断证据保留。

本次仅建立规范和文档衔接；没有迁移既有运行目录、改控制脚本、删除debug材料或清理云端。下面目录为后续新任务建议，不要求把现存历史目录强行改名。

## 1. 三类代码、两类配置

| 对象 | 放置位置与职责 | 不应包含 |
|---|---|---|
| 通用组件 | `tools/<component>/`，控制状态机、基础传输、监控、归档等跨题机制 | 题号、固定主机/GPU、模型秘密、评分常数 |
| 题目适配器 | `<题目>/ops/`或已有私有运行目录，提供启动、评分解析、合法候选与进程归属映射 | 复制整份通用控制器后逐题修改 |
| 一次性排障代码 | `<题目>/ops/incidents/<时间-ID>/scratch/` | 留在项目根、公共工具、冻结题包或正式入口 |
| 非敏感配置 | 题目私有`ops/config/`，运行时冻结一份到run | 密钥、口令、推理中的动态状态 |
| 凭据 | 既有受控凭据接口/指定私有文件；权限最小化 | 公开JSON、argv、日志、镜像、交付ZIP |

现有`tools/research_handoff`是通用云端常驻控制器，通过本地短 SSH 请求管理，也支持本地运行；现有`tools/gpu_monitor`是观测与定向停止工具。两者认证、状态Schema和能力不同。先阅读各自README和源码，不把历史`bundle --profile ...`或旧`research_controller.py`命令写进新操作单。

工具不因名字叫“通用”就自动满足科研合同。模型网关、Harbor容器、全seed判定、计时排除、候选快照和远端子树清理，只有真实实现和验收后才算能力；详细差异见复盘第4节。

## 2. 脚本修改与复用规则

### 2.1 先判断需要改哪里

1. 先查现有入口、CLI帮助、配置Schema、调用方和测试，确认是否仅需改配置。
2. 相同机制跨题复用时，修通用组件；仅题目评分字段/路径不同，修适配器；仅机器/配额/模型变化，改部署配置。
3. 不用全局字符串替换硬改IP、题号、socket、image ID或超时；配置须校验类型、路径、允许值和版本，缺必填项明确失败，不静默回退旧机器。
4. 不在正在运行的控制器目录热覆盖源码。新版本生成新的发布目录和manifest，已有进程继续对应旧源码；紧急修复也须记录实际使用版本及生效范围。
5. 不重写整个运行器以解决一个小问题。先定位失效合同、保留失败原件，再局部修复并跑受影响测试；只有明确重构需求时更换架构。

使用argv列表调用外部命令，默认不经shell；shell确有必要时准确引用参数，不把JSON转义误作shell转义。秘密不出现在命令参数或异常回显中。原子替换状态文件，事件日志追加；单次失败不能截断既有日志或重用评分输出目录。

### 2.2 发布必须可回滚、可识别

发布流程：源文件检查 → 受影响测试 → 生成新bundle → manifest与目标端逐文件核验 → 预检 → 按授权启动。记录组件版本、Schema、文件SHA-256、测试范围、来源和回滚路径。目标已存在且哈希不同，拒绝覆盖；不要靠重跑部署脚本“碰运气修好”。

当前bundle命令（生成组件，不启动研究）：

```bash
python3 tools/research_handoff/bundle.py --output <新的数据盘staging目录>
python3 tools/research_handoff/bundle.py --check <同一staging目录>
```

参数尖括号是占位符，执行前替换为已核验绝对路径。bundle检查源码哈希、可执行权限及额外文件；它不包含题目adapter、模型网关、容器配置和科学评估验收。不要直接修改生成后的受管文件，修改应回到唯一源码源头。

本工作区根当前不是Git仓库；没有commit可用时记录实际文件清单和哈希，不编造commit。未来若采用Git也必须保留真实运行manifest，不能只记分支名或浮动HEAD。

### 2.3 测试覆盖真正的合同

GPU 作业统一复用 [gpu_scheduler](../tools/gpu_scheduler/README.md) 的经校验配置与 API，不为单次实验重写排队或等待脚本。本地控制 Agent 默认采用阻塞式 `submit`；只有需要持续跟踪进度或同时编排多个任务时才使用 `submit_async`/`enqueue`。校验成功但当前资源不足的任务入队，排队上限与父级截止不因重连重置；等待中断后先查原 request/job，不自动重放。控制 Agent 的工具封装也须把调用保持为 pending，单纯启动 CLI 子进程或拿到会话编号不等于 GPU 作业完成。

控制器变更重点验：重复启动排他、单组停止、超时子树清理、guard独立兜底、进程身份复用、预算余额、断线恢复、计时去重、半行JSONL和原子写、上下文交接、失败保留。评分/资源变更则补相应真实Harbor/设备测试。

不要为文档或低影响路径整理重跑长训练。短测试只有证明范围；模拟GPU数据、CPU进程终止、pytest通过都不能替代真实VRAM约束或完整科研结果。

## 3. 配置字段的权威来源

以下是运行声明应包含的信息分类，不是现有工具都接受的JSON Schema；应由题目适配器映射到真实支持字段，不能直接把表头当CLI参数。

| 分类 | 关键内容 |
|---|---|
| 身份 | task/protocol/package版本、run-id、model/group、来源run、源码/资产hash |
| 环境 | 数据盘根与设备、Docker socket、containerd配置、镜像digest、Harbor/CLI可执行路径 |
| 资源 | GPU UUID与配额、CPU/RAM/PID、评分槽数、线程数、存储阈值、退出范围 |
| 模型 | provider/model ID、协议、内部URL、认证引用、推理档位、context容量 |
| 超时 | 连接、读空闲、请求总限、重试、评分、轮次、预算、无进展、guard |
| 接续 | 每组信用来源、候选/计时哈希、容器移交来源、预算原口径及明确覆盖依据 |
| 观测 | 状态/exit路径、阶段指标、心跳/无进展阈值、采样频率、日志分段 |
| 证据 | 原始事件、计时、源码快照、评分与模型、哈希清单、回收位置 |
| 清理 | owner/run标签、允许清理根、临时文件有效期、归档校验与释放条件 |

配置与状态分开：运行时冻结config不原地改；status/latest可以更新；event/trajectory追加；exit只记录真实终态。`latest`仅方便跳转，不承担版本唯一性。

凭据值不写入config快照。记录的是认证方式、secret引用、实际模型及非敏感路由验证结果；避免dump整个环境或provider JSON。当前根有`auth.txt`与`api_key.txt`等私有输入，应从所有构建/发布白名单排除；不能仅依赖忽略文件或“目前没有Git”。本次没有读取这些文件内容。

## 4. 本地工作区建议布局

```text
autoresearch/
  AGENTS.md / AutoResearch出题全流程指引.md / 部署与长程接管.md
  notes/                         # 通用手册、跨题历史复盘，专家私有
  tools/                         # 可复用组件及正式测试
  <task-id>/
    进展清单.md                   # 状态与授权的唯一入口
    ops/                         # 新任务建议采用的私有控制目录
      config/                    # 非敏感源配置与schema说明
      adapters/                  # 薄适配器
      releases/<version>/        # 不可变部署bundle与manifest
      incidents/<time-id>/
        incident.md              # 现象、尝试、原因、结论、保留/清理清单
        evidence/                # 必留日志、命令、差异、测试结果
        scratch/                 # 临时脚本/小型中间文件，用完清理
    runs/<run-id>/               # 回收的运行声明、状态、证据索引
    archive/                    # 已完成运行/旧交付原件，禁止覆盖
    releases/<release-id>/       # 面向交付的冻结候选副本
    delivery/<release-id>/       # 最终ZIP、包外索引与校验结果
```

以上是下一轮可采用布局，已有`research_records/`、`平台修复记录_*/`和`交付包_*/`继续通过索引使用，不为视觉整洁打断历史相对路径。不要在每次操作新建一个顶层`.debug-*`/`.repair-*`目录；已有散落记录按其证据价值登记，确需迁移时保留旧到新映射并更新所有引用。

跨题共同事故可放`notes/<日期-ID>/`；单题诊断回到该题。通用测试放`tools/<组件>/tests/`，真实实验放run，二者不混。输出文件写明确目录，stdout内存小检查无需落debug脚本；需要复用时才把一次性代码晋升为正式工具。

## 5. 云端数据盘布局与本地分工

```text
<已核验数据盘>/autoresearch/
  runtime/                      # 任务专用Docker/containerd及socket
  envs/                         # 锁版本解释器/Harbor等
  cache/                        # 有owner和限额的公共可复用缓存
  tasks/<task-id>/
    releases/<version>/         # 只读公开题包、适配器、部署manifest
    private/                    # solver不可访问的凭据引用/可信资产
    runs/<run-id>/
      launch.json / config.json / manifest.json
      status.json / events.jsonl / exit.json
      agents/<group>/           # 本流候选、轮次、评分索引、STOP、exit
      health/                   # 资源、身份、错误与生命周期
      guard/                    # 独立兜底证据
      tmp/                      # 临时写入，不承载唯一证据
    archive/                    # 已校验、关闭的原始运行归档
```

容器内部`/tmp`也可能写入可写层，需保证该层和实际临时挂载在数据盘；tmpfs使用独立RAM预算。Docker/containerd所有根与日志通过真实进程参数核验。不要只设置一个TMPDIR便认定pip、npm、HF、Harbor和守护进程都已迁移。

本地保留轻量状态、配置、资料、manifest及交付所需回收文件；云端保留高频原件、模型和计算缓存。按需拉取新增归档，回收后核对字节数和hash；监控不反复下载全量模型，不能让四个采集器重复抓同一主机。

## 6. 临时文件生命周期

### 6.1 创建时就写清归属和期限

每次事故至少在incident.md写owner、run/task、用途、创建时间、完成判据、哪些路径是临时、哪些是证据。不硬性要求额外复杂管理系统，目录和一份简短记录足够。临时文件应能明确回答“谁仍在使用、何时可删、删后如何复核结论”。

正常退出时清理本次scratch和中间数据；异常退出时先保留，恢复后再分类。临时文件若已经成为唯一故障重现或修复证据，应归档到evidence，不能仍按临时目录TTL删除。

### 6.2 按价值而不是扩展名清理

| 类别 | 处理 |
|---|---|
| 可再生缓存、pycache、已关闭临时展开目录 | 确认无人使用且不属于交付manifest后，可按作用域删除 |
| 已执行部署/修复脚本 | 若是唯一变更命令证据，保存到事故归档；注记不可用于查询/再次启动 |
| 未采用、无结果的debug脚本 | 记录试验结论后删除；有复用价值则转正式工具并补接口/测试 |
| 失败训练/模型请求、负结果 | 保留原始证据，允许压缩去重，不按失败状态删除 |
| 原始计时、候选源码、评分、全seed模型/重载、Harbor同Trial | 保留；属于科研与交付证据链 |
| 旧发布包和原始质检包 | 不覆盖、不删除；可移到不可变archive并更新索引 |
| 复制出来的重复模型/日志 | 先hash去重，再改引用/归档；不能删唯一文件或破坏相对路径 |
| 含秘密的临时文件 | 按受控接口退出清理；若泄露另行轮换，不复制到事故公开附件 |

### 6.3 清理之前做四个检查

1. 路径经realpath解析仍在本任务允许根内，不跟随未知symlink；owner/run标签明确。
2. 没有存活进程、容器mount、打开日志写入或未完成上传/回收依赖；只检查本任务。
3. 必留原件已归档，manifest、hash和必要的解压/重载验证通过；未验证远端唯一副本不删。
4. 清理列表先预览，实际结果写清路径、原因、时间和保留归档位置；只操作明确白名单。

禁止无范围`pkill`、全局`docker system prune`、清理他人缓存、重启公共服务、删除未知锁、对根目录递归rm。删除自己的无用临时文件是常规维护，但不把该权限扩成删除历史科学证据或他人数据。

## 7. 日志与证据增长控制

状态JSON原子替换，轮次/请求/计时事件追加JSONL。每轮天然独立文件；高频监控按日/体积分段，分段关闭后压缩、hash并索引。不要对活动证据日志使用会丢记录的截断方式，也不把滚动保留数量应用于唯一原始证据。

每段至少关联task/run/group、版本与开始结束时间；索引记录路径、字节数、SHA-256。打包后的归档可复用member索引，不为每份摘要再复制一套模型。公共源码/资产相同可按hash引用，最终交付是否允许外部引用则按平台合同，不能以“去重”为由交付不可访问路径。

当前monitor按日期追加，不自动删除；长期使用须执行本节归档规则。原始训练/评分证据与监控摘要分开，不能仅留下latest.json或终端截图。

## 8. 活动登记和接管资料

一条实际研究流对应一个活动登记。接续时更新run、组级STOP、container ID、状态/exit与预算字段；同一组的旧登记在确认结束后归档。UNKNOWN、失联、身份冲突、仍有进程的登记不能因为过期就删除。

现有`registry.py prune`默认预览，`--apply`才归档并改配置；要求新鲜观测并支持expected-sha256冲突检查。生成快照放本任务明确的monitor/incident目录，避免散落系统`/tmp`。

运行中的monitor保留启动时任务集合，改tasks.json不会自动换集合；按README停止对应本地采集器、validate配置、用新集合重启采集。此操作不停止或恢复云端研究。实际控制器、任务内guard、本地monitor的PID和状态必须分别记录。

接管记录控制在“一份状态入口+证据索引”：最新授权、运行版本、预算余额/截止、查询/停止合同、未完成项、下一步验收标准；不复制多份实时状态表。历史报告顶部标日期和历史属性，避免后人重跑`deploy_launch.py`来“查询”。

## 9. 文档、代码和发布共同完成标准

- 文档命令与实际CLI一致，参数有实现；没有把建议机制写成现有能力。
- 配置、源码与运行manifest可核验；脚本不含题目/机器/密钥硬编码。
- 正式入口、一次性脚本、原始证据与交付副本职责明确。
- 临时文件集中且已清理/归档，失败证据和旧包仍可追溯。
- 路径链接有效，跨目录移动不破坏证据引用；无新散落debug文件。
- 变更只复验受影响合同，不机械重复长训练，也不以短测试替代动态证据。

这些要求用于提高运行成功率和接手效率。目录美观只是结果，真正的验收标准是能准确找到“启动了什么、为何停止、如何证明、还能复现什么”。
