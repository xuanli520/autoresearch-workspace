# AutoResearch 项目预热与交付速查

整理日期：2026-09-25。本文件是通用预热与交付速查，不是任何具体题目的状态、结论或实验授权。题目事实、论文材料和运行证据只放在对应题目私有目录。

2026-09-27补充执行入口：[长程部署与四并发](../部署与长程接管.md)、[脚本/目录治理](长程Agent脚本与目录治理.md)、[最终打包与交付闭环](最终打包与交付闭环.md)。预算以具体题目最新授权及冻结配置为准；打包须区分标准最终包、独立公开任务包与私有运行档案。

## 1. 交付对象

把一个研究问题改造成可持续实验、自动评分、公平可解、可复现的科研任务。

| 对象 | 通用职责 |
|---|---|
| Starter | Agent 可见的起点、接口或合理朴素方法 |
| 正式 Baseline | 同协议、同数据和公平预算下的评分零点 B |
| Reference | 专家私有的可解性证明，不是唯一答案或上限 |
| best_method | 正式研究 Agent 真实探索后，在干净环境复跑的最终方法 |

## 2. 开工前必读与必做

先读 `AGENTS.md`、`AutoResearch出题全流程指引.md`、专家教程、项目培训和适用的 `autoresearch-qa-skills`。根据当前题目再读论文/源码、进展清单、运行说明和许可材料。

开工前写一页选题说明，固定：研究问题、输入输出、允许修改的真实方法空间、固定项、唯一主指标、质量门、Baseline/Reference 假设、U 的事前依据、数据许可、资源/时间预算和 Agent 可见边界。任何没有证据的“可解”“便宜”或“已通过”都先标为待验证。

## 3. 三个内容门

- **G01 方法空间**：接口必须能表达结构、目标、采样、更新、表示或推理策略的真实变化；只开放学习率、轮数或几个权重不合格。题面口号、解析器、guard、调用链和 Reference 差异必须一致。
- **G02 合理 Baseline**：分别说明 Starter、正式 Baseline 和 sanity 对照。核对来源、实现、训练曲线、终止原因、数据、预算、配置、seed、选择规则和指标；简单或旧方法不自动失败，弱化训练或另设低 B 会失败。
- **G03 提升充分**：完整正式 B/R 成对结果有效，Reference 提升稳定，U 有事前依据。随机评估至少 `3σ_B`，`5σ_B` 为强证据；`σ_B` 为 Baseline 原始指标样本标准差（`n-1`）。

正式 seed 全部保留，至少三次，波动大时增加。评分连续、单调、不裁剪；失败状态与正常负分分开。看完结果后不得调整 B、R、U、seed 或质量门。

## 4. 最小可行闭环

Starter 必须在干净环境完成：构建、启动、Public/Dev 评分、原始指标、保存、独立新进程重载、聚合和可信 reward 写出。记录真实硬件、依赖、命令、耗时、峰值资源和错误分类。一次修改到可用反馈尽量不超过两小时；短测只能标 `SMOKE` 或 `DEV_DIAGNOSTIC`。

固定协议后再跑正式 B/R。每个 seed 独立目录，保留 stdout/stderr、result、模型、artifact 哈希和 reload 日志；不能挑 seed、复制 checkpoint 或用占位分数补齐汇总。

## 5. 隔离与 Harbor

研究 Agent 只能看到题面、公开 Starter/数据、Public/Dev 接口和自己的候选；Reference、Hidden、专家证据、另一组轨迹、答案线索、密钥和宿主权限不可见。生成 `qa_exposure_manifest.json`，并核对最终镜像层、挂载、环境变量、Git 历史、符号链接、权限和哈希；删除文件不能消除历史泄露。

选择唯一 Docker/Harbor profile，明确构建 context、COPY、WORKDIR、测试入口和运行时路径。Harbor H01–H04 必查，H05/H06 有运行材料时复核。`tests/test.sh` 必须真实调用 verifier；可信 verifier 原子写 `/logs/verifier/reward.txt` 或数值 `reward.json`。目录存在、TOML 可解析、pytest 通过和静态 QA 通过，都不能写成动态平台验收通过。

若验收要求 H06，`config.json`、`result.json`、verifier reward 文件和非空 Trial 日志必须同属一个 Trial，并与当前任务版本/评分入口一致；检查正常结束和 rewards 数值一致。QA05 若约束每训练进程 GPU 显存，需 provider/宿主侧不可绕过的硬限额及越限记录，PyTorch allocator 设置不够。

## 6. 预算与资源

分别记录云机墙钟、GPU/CPU/磁盘、专家诊断、正式 B/R、两组 Agent、单次评分、容器健康观察、重载和最终复验预算。QA16 两条轨迹各自默认至少 10h；有效时间须由时间段日志复算，记录被排除的排队、安装、故障和阻塞时段及理由。7h 例外只适用于无训练/微调且单轮很短，并须补齐闭环、方向和 best_method 复验材料。每个长任务/阶段墙钟上限不超过 12 小时；有效研究、排队、安装、故障和稳定性不可混算。专家提交前不要求容器连续运行满 12 小时；只需记录实际运行中的健康状态和异常，平台质检可按合同后验验证长时稳定性。

共享 GPU 使用前查询实时占用、PID 和 UUID；绑定授权资源，限制进程/线程/显存/磁盘，使用独立目录和日志。不重启公共服务、不清理他人缓存、不使用无范围杀进程。结束后核对子进程、磁盘和 GPU 显存并释放自己的资源。

在不影响他人的前提下可以继续共享 GPU，不仅因出现其他计算进程就停止自己的训练或要求独占；结合实测峰值、可用显存、负载及调度约定限制自身资源并记录，明确风险/干扰、用户停止和预算到期另按合同处理。

## 7. 冻结前门禁

确认 G01–G03、正式 B/R、独立重载、公开快照、隔离清单、Harbor 接入、reward、退出状态、实际运行健康观察、双 Agent 轨迹、唯一 best_method、三目录、相对路径和哈希均有证据。轨迹每轮 `method_summary` 去除首尾空白后非空；失败轮写真实尝试，纯运行器/请求失败则明确说明，且不改写原始 status/failure_reason/score。QA16 有效时长须由分段日志复算；若任务宣称训练进程 GPU 显存硬上限，须有宿主/provider 越限执行证据。缺一项就补证或退回，不用其他通过项覆盖；训练型重载日志不能留空占位，等价的可追溯记录可接受。连续 12 小时容器稳定性属于平台质检/最终验收，不是提交前专家闸门。

实时状态只维护在题目进展清单；本速查不复制题目名称、方法、seed、主机、PID、分数或历史授权。
