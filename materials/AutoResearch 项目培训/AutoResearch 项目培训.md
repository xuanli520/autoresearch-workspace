# AutoResearch 项目培训

## 一句话理解

**我们要把论文里的一个研究问题，改造成一套 AI 可以持续实验、系统可以自动评分、结果可以复现的科研任务。**

这份文档用于帮助大家快速理解项目。具体字段、命令和验收细节，以 [AutoResearch 专家线下标注教程](https://bytedance.larkoffice.com/docx/P1J5dgIw1oKchcxn29GcvzlMnSd) 和当期任务卡为准。

# 一、项目定位

项目要通过构建benchmark评估大模型的**自动科研能力**：模型拿到一个明确的研究问题、起始代码、数据和计算资源后，能否提出改进想法，把想法写成代码，运行实验，再根据结果继续调整。

项目组提供的论文，可以理解为一份已经完成的研究结果。它证明这个方向有价值、能够做出提升。专家的工作不是复现整篇论文，而是回到研究起点，从中提炼出一个边界清楚、可以运行、可以自动评分的问题，再交给 Agent 自己探索。

**专家的角色：**不是普通标注员，也不是替 Agent 答题，而是负责出题、搭建实验环境、设计评分方式，并证明题目本身是合理的。

# 二、一道完整的题包含什么

- **优化面：来说清楚你希望让Agent干什么，优化哪个目标**。可以理解为我们自己在搞研究的时候，希望提升什么指标（eg 优化基于xx的目标检测算法在xx数据集上的性能）。

- **Baseline：模型从哪里开始，也就是我们论文中的基线方法。** 题目的基准方法，Agent基于这个基准方法开始迭代，提升性能。可以理解为我们平时搞研究过程中的基线方法，我们要对比的方法。（Tips：基线方法可以复用论文中的基线，合理即可。但是基线不能过于简单。）

- **Reference：证明这道题能够改进。**我们给Agent一个任务，首先得确保这个任务可以被完成嘛，不然的话没法衡量Agent是否真正产生了性能提升。所以我们要构建一个参考解，来说明这个任务/优化面是可以被优化的。（Tips：Reference可以复现论文中的代码，也可以自己搓）

- **题面和运行环境：提供一个运行环境。**欸，就像我们跑实验，我们肯定要提供一个相应的运行环境，为了可复现，我们要尽量提供一个docker环境。这边是复用了harbor任务包的规范（什么是Harbor任务包：https://zhuanlan\.zhihu\.com/p/2075161473387587285），主要需要准备：

    - `instruction.md`说明目标、可修改范围、资源限制和提交方式；

    - `environment/`提供依赖、公开数据和只读Starter。

    - `solution/`，Agent在这里修改代码、保存候选方法。

    - `tests/`，用来提供给Agent评估方法的性能，看看自己方法提升没。

### Baseline 要合理

它是普通起点，不是故意做差的起点。不能通过减少数据、训练时间或关键输入来人为制造提升。基线方法可以复用论文中的基线，合理即可。但是基线不能过于简单。

### Reference 要留空间

它只证明题目可解，不是唯一答案，也不是分数上限。Agent 应该有机会超过它。

同时，题目必须开放真正的方法空间。如果只允许调整学习率、训练轮数或几个权重，就更像参数搜索，不符合本项目希望评估的方法创新能力。

## 第一步：确定题目

从论文和代码中切出一个适合 Agent 探索的问题，明确要提升的指标、允许修改的内容、固定内容、资源预算和隔离边界。

**完成标准：**能够一句话说清“Agent 可以改什么、要提升哪个指标、哪些内容不能动”，并且这个问题可以自动评分。

## 第二步：构建任务环境，跑通 Baseline

按照 Harbor/Docker 规范准备题面、依赖、数据、Starter Code、`solution/` 工作区和评分脚本。然后在干净环境中运行未修改的起始方法。

**完成标准：**任务能够在统一环境中一键运行，并得到真实、稳定的 Baseline 分数。

## 第三步：实现 Reference，证明题目可解

专家实现一份有效改进，并与 Baseline 使用相同的数据、随机种子、资源和评测协议进行比较。Reference 可以来自论文方法，也可以是专家验证过的其他合法方法。

如果任务没有其他规定，Baseline 和 Reference 至少各独立运行 3 次；波动大时至少 5 次。不能只挑最好的一次结果。

**完成标准：**Reference 的提升稳定超过随机波动，同时又没有把题目做到接近饱和。

## 第四步：运行两组 Agent 独立迭代

分别运行 **Codex \+ GPT\-5\.6 Sol** 和 **Codex \+ Seed 2\.1 Turbo**。两组使用同一题目、同一公开评分方式和相同资源配置，但必须使用独立输出目录，不能读取对方的轨迹或答案。

默认每个模型组合都要有效运行不少于 10 小时，两组时间不能相加。每轮需要记录尝试的方法、运行状态、实际分数、失败原因和是否刷新当前最佳。

**完成标准：**两组都形成真实、连续、可检查的优化轨迹，并保存各自的最佳方法。

## 第五步：复验最佳方法

比较两组 Agent 产生的有效方法，选择分数最高且符合规则的一份，放入 `best_method/`。随后在全新的干净环境中替换 `solution/` 并重新评分。

**完成标准：**最佳方法脱离原运行现场后仍然能够正常运行并得到分数。

## 第六步：整理材料、质检并提交

整理任务包、Baseline/Reference 证据、两条 Agent 轨迹、运行摘要和最佳方法，再使用项目提供的质检工具检查格式、隔离和材料完整性。

**完成标准：**本地自查没有明显问题，可以交给平台进行正式复现、Hidden Test、防作弊检查和最终验收。专家提交前不要求容器连续运行满 12 小时，也不要求提交 12h soak 报告；专家侧只需确认容器在实际运行中无已知异常并保留健康观察记录。连续 12 小时稳定运行由平台质检/最终验收按合同验证，不是专家侧提交闸门。

# 四、最终交付物

最终交付分成三个相互隔离的部分：

[example\.zip](图片和附件/example.zip)

### workspace/

**可执行题目**

包含题面、环境、起始代码、评分脚本，以及对 Agent 不可见的 Reference。

### expert\_evidence/

**Agent 运行结果**

包含两条独立轨迹、运行摘要、题目标注和唯一最佳方法。

### optimization\_evidence/

**真实性证据**

包含 Baseline/Reference 多次运行结果、原始日志、模型文件和统计汇总。

**简单记忆：**`workspace/` 是题目；`expert_evidence/` 是 Agent 怎么做；`optimization_evidence/` 是我们如何证明这道题真实、可解、不是靠运气。

## 最终目标

**交付一套“问题清楚、环境能跑、系统能评分、过程有记录、结果能复现”的科研任务，让 Agent 在其中真正完成多轮研究和优化。**
