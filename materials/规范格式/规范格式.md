# 规范格式

## 参考格式：目录职责与访问边界固定，内部实现可按优化面扩展

[example\.zip](图片和附件/example.zip)

**本页只规定提交格式。**算法内容、Starter 框架、测试辅助模块、Reference 的内部实现和公开资源可以随题目变化；但目录职责、Agent 可见性、可修改边界和证据真实性要求必须保持一致。附件 `example.zip` 是完整示例。

# 一、最终目录规范

harbor\_task/ 只需要这些文件夹，之前版本如 trust/ 不写进去

```text
submission_root/
├── workspace/
│   ├── harbor_task/                    # Agent 实际可见
│   │   ├── instruction.md
│   │   ├── task.toml
│   │   ├── environment/
│   │   │   ├── Dockerfile
│   │   │   ├── requirements.txt
│   │   │   ├── public_assets/          # train、dev 与任务专用离线资源
│   │   │   └── starter/                # Starter，可为完整代码框架
│   │   ├── solution/                   # Agent 唯一提交目录
│   │   └── tests/                      # 评分文件直接平铺
│   │       ├── grader.py / test.sh
│   │       ├── 按需要可以设置 训练、指标与安全检查模块
│   │       └── hidden_assets/          # 交付时为空，评分时外部注入
│   └── reference/                      # 出题方参考实现，Agent 不可见
├── expert_evidence/                    # Agent 轨迹、最终方法与专家说明
└── optimization_evidence/              # Baseline/Reference 优化面证据
```

# 二、optimization\_evidence 最小提交规范

`optimization_evidence/` 的目标不是记录 Agent 如何搜索，而是在数据、训练、评测、资源和随机种子口径固定时，证明 Reference 相比 Baseline 有真实、稳定、可复现的改善。Reference 不需要是最优方法，也不等于标准答案。

```text
optimization_evidence/
├── README.md                          # 推荐：本目录格式说明
├── 训练证据说明.md                    # 必需：本题实例说明
├── baseline_runs/
│   ├── seed_<真实seed>/
│   │   ├── result.json
│   │   ├── run.log
│   │   └── model/                    # 仅训练型任务存在
│   │       ├── model.<实际格式>
│   │       ├── artifact.json
│   │       └── reload.log
│   └── ...
├── reference_runs/
│   ├── seed_<真实seed>/
│   │   ├── result.json
│   │   ├── run.log
│   │   └── model/                    # 仅训练型任务存在
│   └── ...
└── comparison_summary.json
```

## 2\.1 Seed 与成对运行规则

**Seed 数量不固定为三组。**正式协议声明几个真实 seed，就完整提交几组 Baseline 和几组 Reference；不得抽样、改名、挑最好结果，或把同一 checkpoint 重复当成多轮训练。

- Baseline 与 Reference 必须使用完全相同的 seed 集合，并逐 seed 一一配对。

- 每个 seed 都从初始化独立运行，使用相同数据切分、预处理、预算、指标和质量门。

- 失败或无效运行也应保留原始日志并标记 `INVALID`，不能从汇总中静默删除。

- 制作模板时可使用 `NOT_RUN`，但不得伪造日志、分数或空模型；正式结论只能统计真实完成且有效的运行。

**本附件示例：**正式 seed 为 `20260911` 至 `20260915` 共五个，因此提交 5 组 Baseline 和 5 组 Reference，而不是压缩为三组。

## 2\.2 文件职责

|文件或目录|需要记录什么|
|---|---|
|`README.md`（推荐）|统一定义路径基准、状态、哈希、模型条件和汇总规则。若省略，相关规则必须完整写入训练证据说明。|
|`训练证据说明.md`|用中文说明 Baseline、Reference、允许的优化面、主指标与方向、正式 seed、固定协议、质量门、复现方式、汇总结论和已知记录缺口。|
|`result.json`|单个角色、单个 seed 的主记录；合并保存方法与依赖哈希、协议、训练设置、执行信息、指标、质量门和产物索引。|
|`run.log`|原始 stdout/stderr，包括 warning 和失败信息；不得替换为只剩最终分数的人工摘要。|
|`model/`|仅训练型任务存在，保存该 seed 的真实 checkpoint、完整性说明和独立重载日志。|
|`comparison_summary.json`|汇总全部同 seed 成对结果、均值、样本标准差、改善、显著性判定、聚合质量门和产物完整性。|

## 2\.3 result\.json 最小字段

```json
{
  "schema_version": "...",
  "status": "COMPLETE | INVALID | NOT_RUN",
  "role": "baseline | reference",
  "seed": 12345,
  "task_type": "model_training | non_training",
  "method": {...},
  "protocol": {...},
  "training": {...},
  "execution": {...},
  "metrics": {...},
  "quality_gate": {...},
  "artifacts": {...}
}
```

- `method`：方法名、源码路径、源码 SHA\-256 和必要固定依赖哈希。

- `protocol`：数据边界、训练与评测口径、主指标方向、质量门和资源限制。

- `execution`：实际命令、起止时间、退出码、耗时和资源记录。

- `metrics` 与 `quality_gate`：主指标、诊断指标、有效性和违规项。

- `artifacts`：`run.log`、模型或其他核心产物的相对路径与哈希。

证据路径统一相对提交包根目录。历史记录确实缺少命令、时间或退出码时填 `null` 并说明原因，不能根据结果反推或补造。

## 2\.4 模型产物规则

**训练型任务：**每个 seed 必须保留实际训练得到的模型。`artifact.json` 至少记录模型路径、格式、大小、SHA\-256、对应 role/seed、方法哈希和重载结论；`reload.log` 保存独立进程加载并复评的原始输出。模型缺失、损坏、哈希不一致或不能重载时，该轮不能算完整训练证据。

**非训练型任务：**不创建空 `model/`，在 `result.json` 中将模型产物标记为 `NOT_APPLICABLE`。如果任务会产生其他核心产物，则在 `artifacts` 中记录其路径和哈希。

## 2\.5 comparison\_summary\.json

汇总只能由逐 seed 的真实 `result.json` 计算，至少包含：指标名称和方向、完整 seed 列表、逐 seed Baseline/Reference 值与配对改善、两组均值和样本标准差、平均绝对/相对改善、显著性规则、聚合质量门、模型完整性及源结果路径。

```text
越低越好：paired_improvement = baseline - reference
越高越好：paired_improvement = reference - baseline
正数统一表示 Reference 更好
```

只有正式协议要求的全部成对运行均完成且有效，必要模型均通过重载，汇总状态才能为 `COMPLETE`。

## 2\.6 不再作为最小必交项

`data_manifest.json`、`experiment_plan.json`、`surface_validation.json`、`surface_diff.patch`、`integrity_manifest.json`、`train_config.yaml`、单独的 `run_config.json`/`metrics.json`、`ablation/` 和额外的 `runs/` 中间层，不再属于轻量版最小证据。必要数据说明放在公开资产 manifest 或每轮 `result.json`；消融与额外审计可放入 `expert_evidence/`。
